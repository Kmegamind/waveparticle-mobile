# AI-3 · Stuck story layer

> Part of the [AI index](../AI_00_index.md). Prompt text is the canvas **P3A** ("story layer"), adapted. Two things I changed on purpose are marked **[changed]**. Conflict resolved here: NF6 v4 / runtime design Q6 want an authored obstacle pool and **no model**; the canvas generates the stuck story. Resolution: model first, behind checks, authored pool as fallback (index §2).


> **Update 2026-10-29 (Yue's answers): the two-call option is now the design.** Yue is adding a **Back button on the chat/rest interface** that returns to the task, so there **is** a Resume trigger. Stuck is written at Pause, resolved is written when the user taps Back. His stuck state **lasts until the user returns** (no timed "he went back on his own"), which is the canvas's original fate-link idea. The "one call at Pause" option below is kept as the alternative, not the recommendation. Consequences: the resolved call sits on the user's return path (latency, §8), and the old timed R2 must be reconsidered (§10 new item 5).

## 1. Purpose

When the user **pauses** because they are stuck, he is stuck on something too: one concrete small thing, with a clear cause, not yet resolved. When things move again, it resolves. This is **texture only**: it never changes the decision he faces, never adds a historical event, and never advances his story (fate link). It feeds three places: R1's first message, R2's back-at-work line, and (later) the end line (AI-7) through the run log.

## 4. Prompt blocks and English text

### Option B: one call at Pause (alternative, not chosen; hypothesis)

Block order: INTRO → Background → Goal → He now → Trigger → Requirements → Format. (For option A drop the `back` key from the format; the Resume call writes the resolution.)

```
INTRO (Character)
You are a story writer, writing what is happening to Oppenheimer right now. You do not talk to the user. You only write what is happening on his side.

Background (Character)  [canvas, with the Canyon setting]
Afternoon of November 16, 1942, New Mexico. Oppenheimer and the user are not in the same place. Each has their own goal and their own things to do, and they move forward in sync. You do not know what the user's task is and do not mirror it. The user's state only affects the texture of Oppenheimer's story, not its content.

Goal (Story)
# His overall goal
Get the new laboratory put somewhere my people can actually live, before the Army settles for a canyon too small to hold it.

He now (Story)  [entry state, not a time slice]
# What he is doing now
{{entry.news}}
Why it is not easy: {{entry.why}}

Trigger: stuck (Story)
# What just triggered this
The user got stuck on their own task and paused. Write one concrete small thing that has also got him stuck on his side: a practical, physical or minor snag in the place he is standing, with a clear cause, not yet resolved. Then write one short line for when he gets past it.   [changed: canvas said "related to what he is doing above"; I narrow it to an invented small snag, as NF3 requires]

Requirements (Rules)
- The snag is minor and invented. It is not a historical event, it does not change the decision he faces, and it does not tell the user anything about the story.
- At most two sentences for the snag, one for the line when he is past it.
- Do not add people. The only names are {{names.allowed}}.
- No clock times and no lengths of time.
- He does not know whether the plan will work and does not know anything that happens later.
- Do not repeat these earlier snags: {{used_stuck}}

Output format
Output one JSON object and nothing else:
"story": the snag, first person ("My boots are slipping on the wet gravel.")
"why": why this keeps him from moving, in one short clause
"back": one first-person sentence, at most 14 words, for when he is past it and back at his own work
```

The canvas's example format ("story" + "why") is kept; **`back` is new (hypothesis)** so R2 can show a line without a second call.

### Option A: two calls (CHOSEN; canvas as built)

Same blocks. Pause call writes `story` + `why`. Resume call uses the canvas blocks as they are:

```
Trigger: resolved
# What just triggered this
The user has resumed and is continuing their task.

# The thing he was stuck on
{{story.stuck}}
Why he was stuck: {{story.why}}
Write how this stuck thing got resolved: concrete, with a clear cause.
```

Output: `"story"` = how it resolved, `"why"` = empty. If Resume arrives with no earlier stuck item, the canvas first writes a stuck item (extra call). Option A answers the canvas's fate-link idea ("his relief follows your return") but costs a call at the moment the user is already back at work, and needs a trigger that the wireframes do not have (see §2).

## 5. Output schema

```json
{"story": "string, first person, ≤ 2 sentences, ≤ 20 words (NF3 `obstacle`)",
 "why": "string, one clause",
 "back": "string, first person, ≤ 14 words (NF3 `return`)"}
```

Parse as in the canvas: first `{ … }` in the text, must contain `story`. Flags stored: `source = model | authored`, `rejected_rules[]` (rule IDs only).

## 6. Guardrails

AI-6 rules, **one-way set** (it is his own line, not chat): length and sentence count; no question (R01); no "you" (R04); no "we" (R05); no hook (R06); no clock or duration (R02, R03); no stage words (R10); no dash, "!" or emoji (R11, R12); not ending in an open "…" (R14); probe words (R19); name gate (only `names.allowed`; canvas has a fixed "invented people" list, weaker). Plus two checks the canvas does not have: **not a repeat** of a used stuck item; **snag type**: no historical-event words (hypothesis: a small denylist per story built from the database `happened` nouns of later slices, e.g. for the Canyon "mesa", "school" before c3).

## 7. Fallback

Retry once (canvas behaviour) → authored pair from NF3: `obstacle` (R1) + `return` (R2) for the step's entry state, never reused in the run. Canvas fallback was "use the original time-slice text" (`beat.news`); **do not do that**: it would put a real story fact on the rest page as if it were a snag. Canyon authored fallback examples (pass NF5's script):

| Entry | R1 `obstacle` | R2 `return` |
|---|---|---|
| c1 | My boots are slipping on the wet gravel. I'm finding better footing. | Footing found. Back to the canyon floor. |
| c2 | My hat keeps catching the wind. I'm holding it down. | Held. Back to the argument. |
| c3 | My lighter won't catch in the wind. I'm turning my back to it. | It caught. Back to waiting. |
| c4 | The car is cold. I'm blowing on my hands. | Warmer. Back to the cars. |

(Home's `resolved_short` / `resolved_long` stay authored pool data; they are not generated.)

## 8. Latency and cost

**Option A latency:** the Resume call runs when the user taps Back, so start it on Pause-time idle (hypothesis: pre-generate the resolution at the moment the stuck text is accepted and store it; use it on Back; regenerate only if the user chatted a lot, because chat may have changed the situation). Fallback is the authored `return` line, so Back never waits more than about 1 s.

R1 shows a "moment later" delay by design, so a model call has time to finish: start it **at the moment Pause is tapped**, show R1 with no line yet, and place the message when it passes the checks or at a fixed 2.5 s with the authored fallback, whichever comes first (hypothesis). One call, ≈ 450 input tokens, ≈ 80 output (estimate from canvas block lengths). Option A adds one more call at the user's return and, if Resume came without a Pause, a third.
