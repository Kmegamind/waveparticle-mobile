# AI feature tables and scripts (#436)

The database side of the AI feature pages (`supabase/migrations/20261130000000_ai_features.sql`, `docs/decisions/0032`): `public.ai_features` (one row per feature: `slug`, `position`, `title`, `prompt_keys text[]`, `purpose`, `pass_questions`, `approach` as JSON lists of `{ "text": string, "source": string | null, "draft": boolean }` where `[]` means "Not written yet", `status` one of `not_started`, `exploring`, `passed`, `frozen`, `sections_updated_at`, `sections_updated_by`), `public.ai_feature_status_history` (`feature_slug`, `from_status`, `to_status`, `note`, `changed_by`, `changed_at`) and `public.ai_feature_test_runs` (`feature_slug`, `prompt_key`, `kind` `fake_model` or `real`, `run_at`, `prompt_version`, `pass_count`, `fail_count`, `target_count`, `summary`, `report_path`, `imported_at`). Content editors read all three with `select`; nothing is written through the API except by these functions, both executable by `authenticated`:

- `public.save_ai_feature_sections(target_feature text, new_purpose jsonb, new_pass_questions jsonb, new_approach jsonb) returns void`: content editors (admin or writer); `42501` otherwise, `P0002` for an unknown feature, a check violation for a malformed list. Never changes the status.
- `public.set_ai_feature_status(target_feature text, new_status text, change_note text default null) returns void`: the admin role only (`42501` for a writer, no role or no session); `22023` for an unknown status, `P0002` for an unknown feature, an error when the status is already that value. Writes the history row in the same transaction.

Scripts (print SQL, connect to nothing, never call a model):

- `scripts/ai-features/seed.mjs [--dry-run]`: `parseFeaturePages(markdown)` and `readFeatureSeed(file?)` read section 3 of `docs/ai/AI_11_feature-pages.md` (each `- draft - owner to edit: <text> (source: <file>:<line>)` line becomes an item with `draft: true`); `seedSql(rows, { dryRun })` inserts each feature with status `exploring` only when its slug is missing. `featureSlug(name, keys)`, `quote(text)`, `STATUSES` and `START_STATUS` are exported too.
- `scripts/ai-features/import-runs.mjs [--dry-run] <offline-run folder>`: `readRunFolder(folder)` reads `results.json` (its `meta`), `targets.json` and `report.md` of a #42 run; `summaryStatuses(report)` reads the summary table; `testRunRows(run, { reportPath })` gives one row per feature and prompt key of each suite that ran (`SUITE_FEATURES`: `split` → `plan_split`, `rest` → `rest_reply`, `pause` → `pause_message`), kind `fake_model` unless `meta.mode` is `real`; `importSql(rows, { dryRun })` upserts on (`feature_slug`, `prompt_key`, `kind`, `run_at`). `reportPathOf(folder, root?)` stores the report path relative to the repository when it is inside it.

The e2e Supabase stand-in (`e2e/support/stub-supabase.mjs`) serves the three tables, both functions and `POST /__ai_features { reset?, testRuns? }`; `POST /__ai_features { token, purpose }` shows purpose items to one account only (a layout test that the parallel visual gate must never see).

## The admin pages (#439)

`/admin/ai-features` (ADM-16) lists the 7 features and `/admin/ai-features/<slug>` shows one, read only, to admins and writers (the admin layout's role check and the tables' policies). Both read `public.ai_features` and `public.ai_feature_test_runs` through the signed-in user's own client, and section (e) and the retry_hints fix through `public.list_prompt_versions` at page load, the call of ADM-08 Prompts (`readPromptVersions`, `promptDetail`). The logic is in `src/lib/ai-features/admin.ts`.

## Editing (#453, #430 T6)

Decision AI-PAGE-EDIT: admins and writers edit (a) to (c); only an admin changes the status. Three pages under each feature page, drawn in `docs/design/prototype/admin-ai-features.html`:

- `/admin/ai-features/<slug>/purpose` (AIF-7): (a) purpose and (c) current approach, one box per line with its draft mark and source. `/admin/ai-features/<slug>/pass` (AIF-6): (b), one row per question with Move up, Move down and Remove, and Add question. Save sits in the header action row. The server action (`saveSectionsAction`, logic in `saveFeatureSections` of `src/lib/ai-features/edit.ts`) checks the session and role, reads the stored row and calls `public.save_ai_feature_sections` with the edited sections and the others unchanged. Every line saved from an editor gets `draft: false` and keeps the `source` of the stored line it came from (the browser sends only the line's text and the index of the stored line, never a source); an emptied line is removed; a new line has `source: null`. A save is refused ("changed-since") when `sections_updated_at` is not the one the editor loaded, so a newer save by someone else is not overwritten. The schema has no versions, threshold or red lines, so the drawing's Save draft and Publish are one Save and its Versions panel shows the last save (when, who).
- `/admin/ai-features/<slug>/status` (AIF-5): the four statuses, an optional one-line reason (500 characters at most) and Save status, for admins (`changeStatusAction`, `changeFeatureStatus`, then `public.set_ai_feature_status`). A writer sees the same panel dimmed and disabled, marked "Admin only"; the action refuses a writer before any call and the database function refuses a writer's direct request (`42501`). The history lists each change, newest first (when in UTC, who, from, to, reason), and ends with a "Setup" row: the status the feature started with, at `created_at`. The feature page's (d) says who set the status and when, and links here.

Who made a change is shown as on Publish history (`personName` in `src/lib/publish-history/admin.ts`): the email, else "Account" and the start of the id, else "Deleted account". The email comes from `public.list_ai_feature_people(target_feature text) returns table (user_id uuid, email text)` (`supabase/migrations/20261201000000_ai_feature_people.sql`): the accounts in that feature's status history and its last editor, for content editors only (`42501` otherwise). The tables keep only the account id and `auth.users` is not readable through the API, so this one read function is the only way to show the email. The e2e stand-in serves it, and `POST /__ai_features { token, own: true | null }` gives one account its own copy of the features and their status history, so an editing test never writes a row that another test or the visual gate reads.

## The registry database (#473)

`supabase/migrations/20261202000000_ai_registry.sql` (`docs/decisions/0033`; PRD section 4.14, AI-REGISTRY-STORE, AI-PROMPT-CATEGORY) extends the same tables; there is no second registry table.

- `public.ai_features` adds `feature_id` (unique, `P-01` … `G-05` … `R-07`), `category` (`pipeline`, `gate`, `runtime`), `where_used`, `requirement`, `output_format`, `design_rationale`, `room_to_improve`, `notes` (text; `''` means "Not written yet"), `example_text`, `example_state` (`none`, `candidate`, `confirmed`; a state other than `none` needs text, constraint `ai_features_example_needs_text`), `example_set_by`, `example_set_at`, `fields_updated_at`, `fields_updated_by`. The 7 existing rows get `R-01` to `R-07` (by slug) and `runtime`; their slug, position, title, keys, sections, status and history are not touched.
- `public.ai_feature_field_history` (`feature_slug`, `field`, `old_value jsonb`, `new_value jsonb`, `changed_by`, `changed_at`) and `public.ai_feature_example_history` (`feature_slug`, `example_text`, `example_state`, `set_by`, `set_at`; the newest row is the current example). Content editors read both with `select`; accounts without a role and `anon` read nothing.
- `public.save_ai_feature_fields(target_feature text, new_where_used text, new_requirement text, new_output_format text, new_design_rationale text, new_room_to_improve text, new_notes text) returns void`: content editors; one history row per field that changed; `42501`, `22004` (a null), `P0002`, or a check violation (too long). Never changes the category, status or example.
- `public.set_ai_feature_example(target_feature text, new_text text, new_state text) returns void`: content editors (AI-EXAMPLE-CONFIRM); sets who and when and adds an example history row; `22023` for an unknown state or for `candidate`/`confirmed` with empty text.
- `public.set_ai_feature_category(target_feature text, new_category text) returns void`: the admin role only (`42501` for a writer, no role or no session); `22023`, `P0002`, an error when unchanged; one history row.
- `public.save_ai_feature_sections` keeps its signature and rules and now also writes a history row for each of `purpose`, `pass_questions`, `approach` that changed (FR-AIREG-7). Changes made in the SQL editor (the seed, an undo) write no history.
- `public.prompts.category` (`runtime`, `pipeline`, `gate`; existing rows `runtime`). A new version takes its key's category (trigger `prompts_keep_category`). `public.get_active_prompts` returns runtime rows only; `public.list_prompt_versions()` returns every row and a last column `category` (`PromptVersionRow.category` in `src/lib/prompts/admin.ts`). The app's reader also keeps only the runtime keys it knows (`PROMPT_KEYS`).

Scripts (print SQL, connect to nothing, never call a model; the owner's files are read where they are and never copied):

- `scripts/ai-features/registry-seed.mjs <registry-seed.json> [--dry-run | --check] | --undo`: `parseRegistrySeed(json)` and `readRegistrySeed(file)` give 19 rows; the 12 new slugs are `NEW_SLUGS` (`registrySlug(id, name)`: `p01_find_episodes` …), positions 8 to 19 after the runtime rows' 1 to 7; `registrySeedSql(rows, { dryRun })` inserts the new rows when the slug is missing, with the seed status and no status history row, and fills empty registry fields of the 7 runtime rows; the seed's `example_or_notes` is the example (`notes` stays empty); `BOOK_TEXT_EXAMPLES` (P-04 to P-07, R-02 to R-06) never store their example text, and a row whose stored text is empty gets the state `none` (the dry-run header names the seed's state). `registryCheckSql(rows)` is a read-only comparison; `registryUndoSql()` removes the 12 rows and empties the runtime fields not edited since (`fields_updated_at` and `example_set_at` null).
  - Run log (#476): prompt lab runs are kept when a registry row goes (no cascade), so once one of the 12 rows has a run this undo stops before any change and names it, and the undo of `20261130000000_ai_features.sql` fails; the run log's own undo must come first, and deleting runs loses spend history (`docs/api/ai-runs.md`).
- `scripts/ai-features/import-pipeline-prompts.mjs <prompt-table-source/en> [--seed <registry-seed.json>] [--dry-run | --check] | --undo`: `PROMPT_FILES` maps each row to its key, category and file (S1, S2, S3, S4h, S4f, S4e, cards, S5, S6, S5c, S6c, S7; the seed name's step, with S4 split into h(istorical) and f(ictional), and `scripts/deepseek_cards` as cards); `readPipelinePrompts(folder, { seed })` refuses `proposed4` and, with a seed, a row whose prompt name is not that file; `importPromptsSql` inserts version 1, active, when the key has no row; `importCheckSql` compares active texts by md5; `importUndoSql()` deletes the 12 keys and their Publish history rows.
- `scripts/ai-features/registry-proposed-fix.mjs <registry-seed.json> [--dry-run | --check | --undo]` (#491, AI-PROPOSED-SEED-TEXT): `proposedFixes(json)` lists each stored text field whose seed text names a proposed prompt version (R-02 to R-05, `room_to_improve`), with the old and the new text (`withoutProposedVersions` in `registry-seed.mjs`, which the seed now applies and which refuses a text that still names one). The fix and the undo change a field only while it holds the other text; `--check` is a read-only SELECT that says `fixed`, `old text`, `edited since the seed` or `missing` per field and never prints the texts. Tests: `tests/registry-proposed-fix.test.ts`.

`scripts/ai-features/seed.mjs` (#436) now also writes `feature_id` (`RUNTIME_FEATURE_IDS`) and `category` `runtime` when the table has the registry columns (a `do` block that checks `information_schema.columns`), so it works on a fresh database after this migration and, as before, on one without it.

The e2e stand-in serves the new columns, both history tables and the three functions, keeps a draft's category, answers `get_active_prompts` with runtime rows only, and takes `POST /__prompts { importRows: [{ key, body, category }] }` (removed by `reset`). Tests: `tests/ai-registry-migration.test.ts`, `tests/ai-registry-scripts.test.ts` (invented fixtures in `tests/fixtures/ai-registry/`), `e2e/ai-registry.spec.ts`.

## The registry read view (#474)

Drawn in `docs/design/prototype/admin-ai-features.html` (`#reg-registry`, `#reg-feature`); PRD FR-AIREG-1 to FR-AIREG-4. Read only; it calls no model and writes nothing new.

- `/admin/ai-features` (ADM-16) is the registry: every row of `public.ai_features` with ID, Name, Category, Where it appears, Requirement, Prompt (each key with the version published now and, when one exists, its newest draft, read live through `public.list_prompt_versions`; "view" opens the detail's prompt panel), Status and Example state. Category and status filters, a search over every word the row shows, and Sort by ID (seed order P, G, R; up or down) run in the browser (`registry-table.tsx`, logic in `src/lib/ai-features/registry-filter.ts`). The table scrolls inside its panel with ID and Name sticky. An admin sees Change beside the status of the 7 Runtime rows (it opens the detail's Status section). A failed read shows "The registry could not be read." with Retry; no row shows "No features yet", no match "No feature matches these filters".
- `/admin/ai-features/<slug>` (or `/admin/ai-features/<Feature ID>`, which goes to the slug) shows every field in its own section, "Not written yet" when empty: Purpose and Current approach (Runtime rows only, sections (a) and (c) of #439), Requirement, Prompt (per key: published and draft side by side, `{{variables}}` marked, the changed lines, its category), Output format and rules, Design rationale, Room to improve, Confirmed example (state, who and when, and `public.ai_feature_example_history`), Notes, Pass standard, Status, Version history (`public.ai_feature_field_history` and the status history, newest first), the retry_hints fix (Runtime rows only) and Test results (the imported offline runs of #436). Logic in `src/lib/ai-features/registry.ts`.
- The #453 editors stay on the 7 Runtime rows: the header links to `/purpose` and `/pass`, and the Status section holds the admin's status control (the drawing's place for it) and links to `/status` with its history. Pipeline and Quality gate rows are read only until #475: no links, those three pages answer not found, and `saveFeatureSections` and `changeFeatureStatus` refuse them (`editable` in `src/lib/ai-features/edit.ts`). `featurePrompts` now reads any key (`versionsOf` in `src/lib/prompts/admin.ts`), so Pipeline and Quality gate prompts show their texts.

The e2e stand-in takes `POST /__ai_features { token, registry: true | null }`: that account reads its own 19 rows made from the invented fixtures in `tests/fixtures/ai-registry/` and a fixed prompt list (the seed prompts, the 12 fixture prompts and one draft of `stuck_story`); `__fail_reads` with an AI feature table name fails that read. Tests: `tests/ai-registry-view.test.ts`, `e2e/ai-registry.spec.ts` (#474 block), `e2e/admin-visual-ai-registry.spec.ts` (`test_474_*`, pictures `docs/design/reference/admin/ai-registry-live-<table|feature>-<1024|1280>-{prototype,live,side-by-side}.png`).

## Editing the registry (#475)

PRD FR-AIREG-7, AI-PAGE-EDIT, AI-EXAMPLE-CONFIRM; `docs/decisions/0035`. Every row of every category is edited now (#474's "read only until #475" is gone).

- `supabase/migrations/20261204000000_ai_registry_editing.sql`: `public.save_ai_feature_registry_fields(target_feature text, loaded_at timestamptz, new_name text, new_where_used text, new_requirement text, new_output_format text, new_design_rationale text, new_room_to_improve text, new_notes text) returns timestamptz` (the new `fields_updated_at`): content editors (`42501` otherwise); `22004` for a null, `22023` for an empty name or a name with brackets, `P0002`, `40001` when `fields_updated_at` is not `loaded_at` (someone saved since). The title becomes the trimmed name plus the stored title's bracketed prompt keys (AI-PAGE-TITLES), with a field history row `title`; the six fields go through `save_ai_feature_fields` (one history row per changed field). Never changes the category, the status or the example. The field history's check now accepts `title` (constraint `ai_feature_field_history_field_names`). `public.list_ai_feature_people` also returns the accounts of the field history, the example history, `fields_updated_by` and `example_set_by`.
- `/admin/ai-features/<slug>/fields` (admins and writers): Name and the six text fields, Save in the header and the last save beside them (as AIF-7); the example with None, Candidate or Confirmed and Save example (any role; `set_ai_feature_example`) and its history (when, who, state, text: a replaced confirmed example stays); the category with Save category (admin only; `set_ai_feature_category`; a writer sees it dimmed, "Admin only", disabled); the field history (when, who, field, old, new; a list value one item per line). Logic in `src/lib/ai-features/registry-edit.ts` (`saveRegistryFields`, `setFeatureExample`, `confirmFeatureExample`, `changeFeatureCategory`, `fieldChanges`, `exampleChanges`), server actions in `src/app/admin/ai-features/actions.ts`; each checks the session and role before any call, and the example and fields saves are refused ("changed-since") when the row changed after the page loaded.
- The feature page links "Edit fields" and "Edit pass standard" on every row ("Edit purpose and approach" on Runtime rows only), shows Confirm on a candidate example (any role: the same text becomes confirmed), gives an admin the status control on every row, and links its Version history to the field history. The registry table shows Change on every row for an admin. `/pass` and `/status` open for every row; `/purpose` only for Runtime rows.

The e2e stand-in serves the new function and the wider people list (`e2e/support/stub-ai-registry-editing.mjs`, called once from `stub-supabase.mjs`). Tests: `tests/ai-registry-editing.test.ts`, `e2e/ai-registry-editing.spec.ts`, `e2e/admin-visual-ai-registry-editing.spec.ts` (`test_475_*`, pictures `docs/design/reference/admin/ai-registry-editing-<fields|confirm|fields-writer>-<1024|1280>-{prototype,live,side-by-side}.png`).
